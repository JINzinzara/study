## Topic 1. Docker 이미지와 컨테이너의 차이

### 1. 핵심 개념 요약

Docker 이미지는 애플리케이션 실행에 필요한 파일과 설정을 포함한 템플릿이다.<br>
Docker 컨테이너는 이 이미지를 기반으로 생성된 실제로 실행되는 독립된 환경이며, 하나의 이미지로 여러 컨테이너를 생성할 수 있다.

### 2. 상세 내용

#### Docker 이미지란?

- 컨테이너 실행에 필요한 모든 파일과 설정들을 포함한 템플릿
- 환경 설정 파일, 소프트웨어, DB, 실행 코드, 라이브러리 등


#### Docker 컨테이너란?

- 애플리케이션과 그 실행에 필요한 모든 것을 포함한 가볍고 독립적인 실행 환경 = 도커 이미지가 동작하고 있는 상태
- docker 파일 &rarr; docker 이미지 &rarr; docker 컨테이너
- 특징:
  - 하나의 docker 컨테이너에서는 하나의 프로세스만 포함 시킬 것
  - 기기나 환경에 상관없이 동일한 개발 환결 제공
  - 서비스 리소스에 대한 확장 가능성 및 유연성 보장
  - 한 대의 물리 서버에 여러가지 서비스 배포 가능

#### 이미지와 컨테이너 비교

| 구분 | Docker 이미지 | Docker 컨테이너 |
|------|---------------|-----------------|
| 개념 | 컨테이너 생성에 필요한 템플릿 | 이미지 기반 실행 가능한 인스턴스 |
| 상태 | 실행 불가능 (정적) | 실행·중지·종료 (동적) |
| 변경 가능 여부 | 직접 변경하지 않고 새이미지 빌드 | 쓰기 가능한 계층은 파일과 설정 변경 가능 |
| 역할 | 어플리케이션과 실행 환경을 저장·배포 | 어플리케이션을 격리된 환경에서 실제로 실행 |
| 비유 | 붕어빵을 만드는 틀 | 틀에서 생성된 붕어빵 |

#### 이미지와 컨테이너의 관계

docker 이미지를 통해 동일한 기능을 하는 컨테이너를 여러 대 생성 가능

## Topic 2. Docker Compose의 활용 상황과 Dockerfile과의 차이

### 1. 핵심 개념 요약

Dockerfile은 어플리케이션 실행에 필요한 Docker 이미지를 생성하는 방법을 정의하는 파일이다.<br>
Docker Compose는 여러 컨테이너와 네트워크, 볼륨 등을 하나의 파일에서 정의하고 함께 실행·관리하는 도구이다.<br> 
따라서 여러 서비스로 구성된 개발 환경을 구축할 때 유용하다.

### 2. 상세 내용

#### Docker Compose란?

- 여러 개의 docker 컨테이너를 정의하고 관리하기 위한 도구
- 컨테이너 생성을 위한 정보들을 YAML 파일에 정의하여 여러 컨테이너를 한 번에 실행
- 여러 docker 어플리케이션 산 상호작용 혹은 의존적일 때 관리 가능

#### Docker Compose가 유용한 상황

- 웹 서버, 데이터베이스 등 여러 서비스가 함께 필요한 경우 &rarr; 다수의 컨테이너들이 필요한 마이크로 서비스 관리에 유용
- 개발 환경을 동일하게 구성해야 하는 경우
- 여러 컨테이너를 한 번에 실행·종료해야 하는 경우

#### Dockerfile과 Docker Compose 비교

| 구분 | Dockerfile | Docker Compose |
|------|------------|----------------|
| 목적 | Docker 이미지를 만드는 과정 정의 | 여러 컨테이너의 실행 환경·관계 정의 |
| 관리 대상 | 하나의 Docker 이미지 | 여러 컨테이너와 네트워크·볼륨 |
| 주요 설정 내용 | 베이스 이미지, 파일 복사, 패키지 설치, 실행 명령어 | 사용할 이미지, 포트, 환경 변수, 볼륨, 서비스 의존 관계 |
| 사용 시점 | 어플리케이션의 이미지 로드 | 여러 서비스를 함께 실행·관리 |
| 대표 명령어 | `docker build` | `docker compose up/down` |

#### Dockerfile과 Docker Compose의 관계

Dockerfile과 Docker Compose는 서로 상호 보완적인 도구<br>
Dockerfile로 서비스의 이미지를 반들고, Docker Compose로 해당 이미지들을 컨테이너로 실행

## Topic 3. Kubernetes의 기본 개념과 Docker와의 관계

### 1. 핵심 개념 요약

Kubernetes는 여러 서버에 분산된 컨테이너를 자동으로 배포하고 관리하는 컨테이너 오케스트레이션 플렛폼이다.<br>
Docker가 어플리케이션을 이미지와 컨테이너로 만드는 역할이라면, Kubernetes는 많은 컨테이너의 배포, 확장, 네트워크 연결 및 장애 복구를 담당한다.

### 2. 상세 내용

#### Kubernetes란?

- 다수의 컨테이너화 된 워크로드와 서비스를 효율적으로 다루기 위한 오픈소스 기술/플랫폼
- 대규모 어플리케이션을 배포할 수 있도록 컨테이너의 네트워킹 및 관리를 자동화하는 프로세스
- Kubernetes를 사용하는 이유:
  - 무중단(Fault tolerance) 제공: self-healing기능으로 서비스 중단이 없고, 어플리케이션 업데이트 가능
  - Vendor Lock In 해결: 특정 클라우드 환경에 구애받지 않음
  - 효율적인 자원 사용
  - 유연한 확장성

#### Kubernetes의 주요 구성 요소

| 구성 요소 | 역할 |
|-----------|------|
| Cluster | 여러 Node를 하나의 환경으로 묶은 집합체 |
| Node | Pod가 동작하고 실행되는 서버 |
| Pod | 하나 이상의 컨테이너를 그룹화한 최소 배포 단위 |
| Deployment | Pod의 배포, 복제, 업데이트 및 장애 복구 상태 관리 |
| Service | 여러 Pod에 고정된 접근 경로를 제공하고 요청을 분산 |

#### Kubernetes의 주요 기능

- 자동 스케일링(Auto-scaling): 트래픽이 늘면 CPU나 메모리 사용량을 분석하여, 자동으로 컨테이너의 수를 늘려 리소스를 최적화
- 자동 복구(Auto-healing): 실행 중인 컨테이너가 다운되거나 문제가 생기면 자동으로 재시작/교체
- 로드 밸런싱(Load Balancing): 트래픽이 늘면 자동으로 여러 컨테이너와 노드에 트래픽 배분
- 선언적 관리(Declarative Configuration): 관리자가 원하는 상태를 Kubernetes가 자동으로 조정
- 높은 이식성(Portability): 특정 클라우드 없체에 종속되지 않고, 다양한 환경에서 동일하게 작동

#### Docker와 Kubernetes의 관계

| 구분 | Docker | Kubernetes |
|------|--------|------------|
| 주요 목적 | 어플리케이션을 이미지로 만들고 컨테이너로 실행 | 여러 컨테이너를 자동으로 배포/운영 |
| 관리 범위 | 개발 호스트의 이미지와 컨테이너 | 여러 Node로 구성된 Cluster 전체 |
| 담당 역할 | 이미지 빌드, 배포 및 컨테이너 실행 | 컨테이너 배치, 확장, 네트워크 연결 및 장애 복수 |

Docker는 만든 이미지를 Kubernetes 환경에서도 사용할 수 있으며, Kubernetes는 해당 이미지를 기반으로 컨테이너를 여러 서버에 배포하고 관리

## Topic 4. 딥러닝 모델을 ONNX·TensorRT 포맷으로 변환하는 이유

### 1. 핵심 개념 요약

학습에 사용한 모델은 프레임워크와 실행 환경에 의존하므로 실제 서비스 측면에서 속도와 호환성 문제가 발생할 수 있다.<br>
ONNX로 변환하면 서로 다른 프레임워크와 실행 환경에서 모델을 활용할 수 있고, TensorRT를 사용하면 NVIDIA GPU 환경에 맞게 모델을 최적화하여 추론 속도와 자원 효율을 높일 수 있다.

### 2. 상세 내용

#### 모델 포맷 변환이 필요한 이유

- 학습 환경과 서비스 환경의 차이
- 추론 속도 및 자원 사용량 개선
- 다양한 하드웨어와 프레임워크 간 호환성 확보 &rarrr; 학습(PyTorch/TensorFlow)과 배포(TFLite/CoreML/TensorRT) 프레임워크가 다름

#### ONNX란?

- 서로 다른 ML 프레임워크에서 개발된 모델을 서로 호환할 수 있도록 하는 표준 모델 포맷(by meta, ms)
- 구성 요소: 
 - Graph: 연산 그래프 (Node + 간선)
 - Node: 개발 연산 (Conv, ReLU, MatMul등)
 - Tensor: weight, activation layer
 - Opset: 연산자 버전 (호환성 관리)
- 표준, 광범위한 지원

#### TensorRT란?

- 고성능 딥러닝 추론 라이브러리 (by NVIDiA)
- 다양한 딥러닝 프레임워크에서 학습된 모델을 가져와 GPU에서 최적화된 엔진 형태로 변환하고 실행
- 모델을 하드웨어에 맞게 최적화하여 짧은 지연 시간과 높은 처리량의 추론 가능

#### 모델 포맷 비교

| 구분 | 기존 학습 모델 | ONNX | TensorRT |
|------|----------------|------|----------|
| 주요 목적 | 모델 학습과 실험 | 프레임워크 간 모델 교환 및 배포 | NVIDIA GPU 기반 고성능 추론 |
| 호환성 | 학습에 사용한 프레임워크에 의존 | 다양한 프레임워크와 실행 환경 지원 | NVIDIA GPU의 CUDA 환경에 의존 |
| 실행 환경 | PyTorch, TensorFlow등 원래 학습 환경 | ONNX를 지원하는 환경 | TensorRT가 설치된 NCIDIA GPU 환경 |
| 성능 최적화 | 별도 최적화 없다면 학습 환경 준수 | Graph 최적화의 다양한 실행 제공자 활용 | 연산 결합, 메모리 최적화, FP16-INT8 변환 등 |
| 활용 상황 | 모델 개발, 학습 및 성능 검증 | 여러 플랫폼에 모델을 배포하거나 프레임워크 의존성을 줄일 떄 | 낮은 지연 시간이 필요할 때 |

#### 변환 시 고려할 점

- 지원하지 않는 연산자: 원본 모델에 ONNX나 TensorRT가 지원하지 않는 연산자 포함 시, 변환 실패 또는 별도의 연산자 구현 필요
- 모델 정확도: FP16이나 INT8과 같이 낮은 정밀도 사용 시, 출력값과 정확도가 변화할 수 있음 &rarr; 변환 전후의 성능 비교
- 하드웨어 및 실행 환경 의존성: GPU 종류, CUDA·TensorRT 버전, 운영체제 등에 따라 모델의 실행 가능 여부와 성능 변화

## Topic 5. PTQ와 QAT의 차이

### 1. 핵심 개념 요약

PTQ는 학습이 끝난 모델을 별도의 재학습 없이 양자화하는 방식으로, 적용이 빠르고 간단하지만 정확도 손실이 비교적 크다.<br>
QAT는 학습 과정에서 양자화로 발생할 오차를 미리 반영하여 모델을 조정하므로 정확도는 잘 유지되지만, 추가 학습 데이터와 시간이 필요하다.

### 2. 상세 내용

#### 양자화란?

- 신경망에서 weight와 activation의 정밀도를 줄이는 것
- 대부분의 기존 모델은 FP32 형식이고, 양자화 적용시 INT8등의 더 적은 비트로 변환 가능 &rarr; 모델 계산 및 메모리 사용량 저하, 추론 속도 상승
- 모델의 크기가 크다는 것은 비트 수가 많아 모델의 정확도 상승. 반면 양자화 후 비트 수가 줄어 들면 정밀도가 저하되며 모델의 정확도도 동시에 저하

#### Post-Training Quantization이란?

- 모델을 춘련 종료 후, weight를 변환
- 적용 과정:
  1. 학습이 완료된 FP32 모델 준비
  2. 목표 정밀도와 양자화 방식 선택
  3. 필요한 경우 대표 데이터로 값의 범위를 보정(calibration)
  4. 모델을 FP16, INT8 등의 형식으로 변환
  5. 변환 전후의 정확도와 추론 성능을 비교
- 장점: 학습 시간이 QAT 대비 짧음. 적용 난이도가 낮음
- 단점: QAT 대비 성능 저하가 높음 &rarr; 정확도 저하 가능성

#### Quantization-Aware Training이란?

- 모델 학습 중 시뮬레이션을 통해 최적의 양자화 과정을 거힘
- 파이프라인:
  1. 사전학습 모델 로딩(FP32)
  2. Fake Quantize 노드 삽입
  3. 미세조정 학습 (원본의 1~10% epoch, 낮은 학습률)
  4. 양자화 모델 배포 
- 장점: PTQ 대비 성능 저하가 낮음 &rarr; 정확도 높음
- 단점: 추가 학습을 위한 데이터와 연산 자원이 필요하며 구현 난이도와 학습 시간이 증가

#### PTQ와 QAT 비교

| 구분 | PTQ | QAT |
|------|-----|-----|
| 적용 시점 | 모델 학습 후 | 모델 학습 중 |
| 추가 학습 필요 여부 | 일반적으로 불필요 | 필요 |
| 구현 난이도 | 쉬움 | 어려움 |
| 적용 시간 | 짧음 | 김 |
| 정확도 손실 | 0.5~2% | 0.1~0.5% |
| 적합한 상황 | 빠른 배포, 큰 모델 | 최대 정확도, 저비트(INT4) |

#### 기법 선택 기준

PTQ 먼저 시도 &rarr; 정확도 부족할 시 QAT로 전환

## Topic 6. 모델 경량화 후 성능 검증 절차

### 1. 핵심 개념 요약

모델 경량화 후에는 모델 크기와 추론 속도 뿐만 아니라 정확도와 서비스 안정성도 함께 검증한다. 동일한 데이터와 조건에서 원본 모델을 기준으로 비교하며, 실제 서비스 하드웨어와 트래픽 환경에서도 요구사항을 충족하는지 확인한다.

### 2. 상세 내용

#### 검증이 필요한 이유

- 양자화, 가지치기(Puruning), 연산 최적화 과정에서의 수치 오차로 모델 정확도 낮아짐
- 개발 환경과 실제 서비스 환경을 하드웨어, 라이브러리 버전, 요청량 등이 달라 성능 측정 결과 변화
- 전체 평균 지표만 확인하면 클래스, 예외 입력 또는 응답 시간이 긴 요청에서 발생하는 문제 발견 어려움
- 경량화로 모델 크기가 줄어도 실제 하드웨어가 해당 연산을 지원하지 않으면 의미 없음

#### 모델 품질 비교

| 확인 항목 | 확인 내용 | 비교 결과 |
|-----------|-----------|-----------|
| 정확도 | 경량화 전후 주요 평가 지표(Accuracy, F10score, mAP) 비교 | 서비스에서 정한 허용 범위 이내 |
| 출력 일치도 | 동일 입력에 대한 예측 결과 비교 | 정해진 오차 범위 이내 |
| 클래스별 성능 | 특정 클래스의 성능 저하 여부 | 중요 클래스의 최소 기준 충족 |
| 경계 사례 | 이상치와 예외 입력의 처리 결과 | 새로운 치명적 오류 제거 |

#### 추론 성능 비교 항목

- 모델 크기
- 평균 지연 시간
- 처리량 
- 메모리 사용량 
- CPU·GPU 사용량 

#### 실제 서비스 환경 테스트

- 실제 배포에 사용할 하드웨어와 런타임에서 모델 테스트
- 살재 데이터 분포를 반영한 calibration 데이터셋으로 정확도 측정
- 워밍업 후 여러 차례 반복 측정 &rarr; 안정적인 성능 결과
- 동시 요청과 최대 예상 트래픽 적용하여 부하 테스트 수행
- 평균 응답 시간 및 지연 시간 확인
- 장시간 실행에 대한 메모리 누수, 성능 저하 및 비정상 종료 여부 확인
- 입력 크기와 배치 크기 변경하며 서비스 요구사항 충족을 확인

#### 배포 후 모니터링

- 응답 시간, 처리량, 오류 &rarr; CPU, GPU 사용량 트래킹
- 입력 데이터 분포를 학습 및 검증 데이터로 비교
- 기존 모델과 경량화 모델을 shadow 테스트, A/B 데스트, 카나리 배포 방식으로 비교
- 실제 사용자 환경에서 클래스별 성능과 비정상 결과 확인
- 허용 범위에서 벗어날 시의 롤백 기준과 절차 준비

#### 최종 확인 체크리스트

- [ ] 경량화 전후 모델의 정확도를 비교했는가?
- [ ] 주요 클래스와 경계 사례를 별도로 확인했는가?
- [ ] 실제 배포 하드웨어에서 성능을 측정했는가?
- [ ] 지연 시간과 처리량이 서비스 요구사항을 충족하는가?
- [ ] 메모리와 CPU·GPU 사용량을 확인했는가?
- [ ] 배포 후 모니터링 및 롤백 기준을 마련했는가?
